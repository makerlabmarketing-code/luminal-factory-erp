## 2. Exact production changes

The forward transaction:

1. Fails before mutation unless `projects`, `phases`, `employees`, and `can_view_project(bigint)` exist; phase project references are valid; `(project_id, order_index)` is unique; and every existing status is recognized.
2. Adds four columns to `public.phases` if absent: `status text`, `completed_at timestamptz`, `updated_at timestamptz`, and `updated_by_employee_id bigint`.
3. Deterministically maps compatibility statuses, fills missing `updated_at`, makes `status` and `updated_at` non-null, and installs the final status constraint and employee FK.
4. Creates `public.phase_status_history`, its constraints and index.
5. Creates the service-role-only transactional RPC `public.transition_project_phase_status(...)` that locks the phase, verifies project/current status, updates the phase, and inserts exactly one history row in the same transaction.
6. Enables RLS on history, removes browser mutation access, grants authenticated users SELECT only, and limits rows through `can_view_project(project_id)`.

No project, task, project-member, employee, Auth, attendance, payroll, finance, or storage row is inserted, updated, or deleted.

## 3. Exact database objects affected

### Existing table `public.phases`

Columns added or normalized:

- `status text not null default 'LOCKED'`
- `completed_at timestamptz null`
- `updated_at timestamptz not null default now()`
- `updated_by_employee_id bigint null`

Constraints:

- `phases_status_check`: status in `ACTIVE`, `LOCKED`, `COMPLETED`, `BLOCKED`, `REVIEW`, `CANCELLED`.
- `phases_updated_by_employee_id_fkey`: `updated_by_employee_id -> employees(id) ON UPDATE CASCADE ON DELETE SET NULL`.

Indexes:

- `phases_project_order_idx (project_id, order_index)`.
- `phases_project_status_idx (project_id, status)`.

Rows affected: only existing phase rows requiring status compatibility mapping and/or a missing `updated_at` value.

### New table `public.phase_status_history`

Columns:

- `id bigint generated by default as identity primary key`
- `project_id bigint not null -> projects(id) ON UPDATE CASCADE ON DELETE CASCADE`
- `phase_id bigint not null -> phases(id) ON UPDATE CASCADE ON DELETE CASCADE`
- `actor_employee_id bigint not null -> employees(id) ON UPDATE CASCADE ON DELETE RESTRICT`
- `action text not null`
- `old_status text null`
- `new_status text not null`
- `reason text not null`
- `note text null`
- `override_flag boolean not null default false`
- `created_at timestamptz not null default now()`

Constraints:

- `phase_status_history_action_check`
- `phase_status_history_new_status_check`
- `phase_status_history_reason_check`
- the primary key and three foreign keys above

Index: `phase_status_history_project_phase_created_idx (project_id, phase_id, created_at desc)`.

RLS policy: `phase status history project view select`, SELECT to `authenticated` using `public.can_view_project(project_id)`. There are no browser INSERT/UPDATE/DELETE/ALL policies.

### Function

`public.transition_project_phase_status(bigint,bigint,bigint,text,text,text,text,text,boolean)` is `SECURITY DEFINER`, uses `search_path = public, pg_temp`, is executable only by `service_role`, performs a row lock/concurrency check, updates one matching phase, and inserts one history row atomically.

Triggers: none are created or changed by the authoritative 2026-07-21 package.

## 4. Exact backfill behavior

For each `public.phases` row:

- `completed_at is not null` -> `COMPLETED`.
- Otherwise `IN_PROGRESS` -> `ACTIVE`.
- Otherwise a null or `NOT_STARTED` status with `order_index = 0` -> `ACTIVE`.
- Otherwise a null or `NOT_STARTED` status -> `LOCKED`.
- Existing `ACTIVE`, `LOCKED`, `COMPLETED`, `BLOCKED`, `REVIEW`, and `CANCELLED` remain unchanged.
- Missing `updated_at` becomes the transaction timestamp.
- No history row is synthesized for backfill.
- No assignee, deadline, task, membership, or employee data is inferred.

Orphans, duplicate project/order positions, or any unknown status block the transaction before schema mutation.

## 5. Expected row counts

Let pre-run `phase_row_count = N`, `null_or_legacy_status_count = B`, `missing_updated_at_count = U`, and `phase_history_row_count = H`.

- `public.phases` before: `N`; after: exactly `N`.
- Phase rows updated by status backfill: exactly `B` (a subset may also be in `U`).
- Phase rows updated only to fill `updated_at`: `U - overlap(B,U)`.
- `public.phase_status_history` before: absent or `H`; immediately after rollout: `H` (normally `0` on first creation).
- Each successful post-activation transition: phase count stays `N`; history count increases by exactly `1`.
- Project/task/member/employee/attendance/payroll/finance row counts: unchanged.

The numeric values are intentionally `BLOCKED` until the read-only pre-run script is executed and attached to the approval record.

## 6. Rollback limitations and data-loss risks

The rollback removes the history read policy, history index/table, transition RPC, phase status index, final status check, and updated-by FK. It deliberately preserves the four phase columns and their values.

Limitations and risks:

- Dropping `phase_status_history` permanently deletes all transition audit rows. Export is required before rollback once any transition has occurred.
- The rollback does not restore pre-backfill status values (`NULL`, `NOT_STARTED`, or `IN_PROGRESS`). That mapping is not reversible without a captured pre-run row snapshot.
- The rollback leaves phase status/timestamps in place to avoid further data loss; it is not a byte-for-byte schema restoration.
- Dropping columns or restoring historical constraints requires separate destructive approval.
- If application flags remain enabled after rollback, reads/mutations will fail. Disable both flags first.
